# Phase 20 — PostgreSQL 19 Enterprise HA/DR Architecture on RHEL 10

This phase takes PostgreSQL 19 from **single-server administration to production-grade High Availability and Disaster Recovery**.

The key distinction:

* **HA** → minimize downtime when the primary server fails.
* **DR** → recover from a site/region-level disaster.
* **Backup** → recover from logical corruption, accidental deletion, ransomware, etc.
* **Replication alone is not a backup.**

---

## 20.1 Enterprise HA/DR Reference Architecture

```text
                         APPLICATIONS
                              |
                    +---------+---------+
                    |                   |
              Connection Pool       VIP/DNS
                    |                   |
                    +---------+---------+
                              |
                              v
                     PRIMARY - DC1
                     PostgreSQL 19
                           |
                Streaming Replication
                 /                   \
                /                     \
               v                       v
       STANDBY-01 DC1             STANDBY-02 DC1
       PostgreSQL 19              PostgreSQL 19
       Sync/Async                Async
                                     |
                                     |
                              WAN Replication
                                     |
                                     v
                              DR - DC2
                              PostgreSQL 19
                                   |
                             DR Standby
```

A production design should separately define:

```text
HA
DR
Backup
Monitoring
Failover
Client routing
Fencing
```

# 20.2 RPO vs RTO

These two terms drive the architecture.

### RPO — Recovery Point Objective

How much data loss is acceptable?

Example:

```text
RPO = 0
```

means the business requires no committed-data loss under the defined failure scenario.

### RTO — Recovery Time Objective

How quickly must service be restored?

Example:

```text
RTO = 5 minutes
```

means the service must be restored within five minutes.

# 20.4 PostgreSQL Replication Model

PostgreSQL physical streaming replication works approximately as:

```text
PRIMARY
   |
   | WAL
   v
WAL Sender
   |
   | Streaming
   v
WAL Receiver
   |
   v
Standby WAL
   |
   v
Replay
   |
   v
Standby Database
```

The standby continuously receives WAL generated by the primary and replays it.

---

# 20.5 Primary vs Standby

### Primary

Accepts:

```text
INSERT
UPDATE
DELETE
DDL
```

### Physical Standby

Normally:

```text
Read-only
```

and continuously replays WAL.

Architecture:

```text
              PRIMARY
                 |
             WAL stream
                 |
                 v
              STANDBY
                 |
              Replay
                 |
                 v
          Database state
```

---

# 20.6 Synchronous Replication

With synchronous replication:

```text
Application
     |
     v
Primary
     |
     +------ WAL ------> Standby
     |
     v
Commit confirmation
```

The primary can wait for the configured synchronous standby to acknowledge WAL according to the configured `synchronous_commit` behavior.

This can reduce data-loss exposure but introduces dependency on standby/network latency.

---

# 20.7 Asynchronous Replication

```text
Application
     |
     v
Primary
     |
     +---- WAL ----> Standby
     |
     v
Commit
```

The primary does not wait for the standby to complete the corresponding synchronous acknowledgement.

Advantages:

```text
Lower commit latency
Better geographic flexibility
Less dependency on WAN latency
```

Trade-off:

```text
Potential replication lag
Potential data loss during primary failure
```

---

# 20.8 Synchronous vs Asynchronous

| Feature                 | Synchronous                             | Asynchronous                        |
| ----------------------- | --------------------------------------- | ----------------------------------- |
| Commit dependency       | Standby acknowledgement can be required | No standby acknowledgement required |
| Data-loss exposure      | Can be minimized substantially          | Can exist if standby is behind      |
| Latency                 | Higher                                  | Lower                               |
| WAN suitability         | Requires careful design                 | Generally easier                    |
| Availability dependency | Higher                                  | Lower                               |
| Typical use             | Critical HA                             | DR / read replicas                  |

The exact durability semantics depend on PostgreSQL's `synchronous_commit`, synchronous standby configuration, and failure scenario.

# 20.9 PostgreSQL 19 Configuration

Primary:

```conf
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
```

For synchronous replication, configure the appropriate:

```conf
synchronous_standby_names = '...'
```

and choose the desired:

```conf
synchronous_commit = ...
```

Do not blindly copy production values; these parameters must match the number of replicas and the required durability model.

---

# 20.10 Replication User

Create a dedicated role:

```sql
CREATE ROLE replicator
WITH REPLICATION
LOGIN
PASSWORD 'CHANGE_ME';
```

Use a dedicated replication identity rather than using the `postgres` superuser.

# 20.11 `pg_hba.conf`

On the primary, permit the standby's replication connection.

Conceptually:

```conf
host    replication    replicator    STANDBY_IP/32    scram-sha-256
```

Then reload:

```bash
sudo systemctl reload postgresql-19
```

Validate configuration before relying on it.

---

# 20.12 Replication Slot

Create a physical replication slot:

```sql
SELECT pg_create_physical_replication_slot('standby01_slot');
```

Check:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots;
```

---

# 20.13 Why Replication Slots Matter

Without appropriate WAL retention:

```text
Primary
   |
   v
WAL generated
   |
   v
Standby disconnected
   |
   v
Required WAL removed
   |
   v
Standby cannot continue
```

A replication slot can retain required WAL.

But:

> A forgotten inactive slot can cause WAL to accumulate until the filesystem fills.

Therefore slot monitoring is mandatory.

---

# 20.14 Building a Standby

Stop PostgreSQL on the new standby if necessary:

```bash
sudo systemctl stop postgresql-19
```

Ensure the target data directory is appropriate and empty for the base backup.

Then:

```bash
sudo -u postgres pg_basebackup \
    -h PRIMARY_IP \
    -U replicator \
    -D /var/lib/pgsql/19/data \
    -Fp \
    -Xs \
    -P \
    -R
```

`-R` writes the recovery configuration required for the resulting cluster to connect back to the primary.

---

# 20.15 Start Standby

```bash
sudo systemctl start postgresql-19
```

Check:

```bash
sudo systemctl status postgresql-19
```

# 20.20 Cascading Replication

Instead of:

```text
PRIMARY
 | \
 |  \
 v   v
S1   S2
```

you can design:

```text
PRIMARY
   |
   v
STANDBY-01
   |
   v
STANDBY-02
```

This can reduce the number of direct replication connections from the primary.

Use cases include geographically distributed architectures.

---

# 20.21 Cascading Replication Consideration

Potential benefit:

```text
Primary replication workload
        ↓
Reduced direct fan-out
```

Potential drawback:

```text
Primary
   ↓
Standby A
   ↓
Standby B

Failure of A
   ↓
B loses upstream
```

Therefore cascading topology needs explicit failure planning.

---

# 20.22 Multi-Standby Architecture

A common enterprise design:

```text
                   PRIMARY
                  /       \
                 /         \
                v           v
          SYNC STANDBY   ASYNC STANDBY
             DC1             DC1
                              |
                              |
                              v
                          DR STANDBY
                             DC2
```

Possible purposes:

```text
SYNC standby → HA
ASYNC standby → read scaling / additional protection
DR standby → site disaster
```

# 20.23 Failover

Failover means:

```text
Primary unavailable
       ↓
Standby promoted
       ↓
Standby becomes primary
       ↓
Applications redirected
```

Example:

```text
BEFORE

Primary A
   |
   v
Standby B


AFTER

Primary B
```

# 20.24 Manual Promotion

On the selected standby:

```bash
sudo -u postgres pg_ctl \
    -D /var/lib/pgsql/19/data \
    promote
```

Or use the PostgreSQL SQL interface:

```sql
SELECT pg_promote();
```

Verify:

```sql
SELECT pg_is_in_recovery();
```

Expected after promotion:

```text
f
```

---

# 20.25 The Dangerous Part — Old Primary

Suppose:

```text
Primary A
    X
    |
    | network partition
    |
Standby B
```

If B is promoted while A is actually still accepting writes:

```text
A → writes
B → writes
```

You now have **two writable timelines**.

This is the classic split-brain problem.

---

# 20.26 Split-Brain

```text
             NETWORK FAILURE
                  |
          +-------+-------+
          |               |
          v               v
       Server A        Server B
       PRIMARY         PROMOTED
          |               |
       WRITE             WRITE
          |               |
          +-------X-------+
```

The resulting divergence cannot simply be resolved by "turning replication back on."

---

# 20.27 Fencing

Before promoting a standby, the old primary must be prevented from serving writes.

Common enterprise mechanisms include:

```text
STONITH
Power fencing
Cloud instance isolation
VM shutdown
Hypervisor fencing
Network isolation
Load-balancer removal
VIP removal
Application routing controls
```

The exact mechanism depends on infrastructure.

---

# 20.28 Failover Sequence

A controlled failover should look like:

```text
1. Detect primary failure
        ↓
2. Confirm failure
        ↓
3. Fence old primary
        ↓
4. Confirm old primary cannot accept writes
        ↓
5. Select standby
        ↓
6. Promote standby
        ↓
7. Validate database
        ↓
8. Redirect clients
        ↓
9. Validate application
        ↓
10. Rebuild former primary as standby
```

---

# 20.29 Switchover

Switchover is planned.

```text
PRIMARY A
    |
    v
STANDBY B
```

You intentionally move production:

```text
PRIMARY B
    |
    v
STANDBY A
```

Typical reasons:

```text
OS maintenance
PostgreSQL maintenance
Hardware maintenance
Datacenter maintenance
Testing
Planned DR exercise
```

---

# 20.30 Failover vs Switchover

|                  | Failover            | Switchover                 |
| ---------------- | ------------------- | -------------------------- |
| Planned?         | Usually no          | Yes                        |
| Primary healthy? | Usually unavailable | Yes                        |
| Objective        | Restore service     | Controlled role transition |
| Risk             | Higher              | Lower                      |
| Validation       | Critical            | Critical                   |
| Fencing          | Often required      | Still important            |

# 20.31 DR Architecture

For geographically separate DR:

```text
                 PRIMARY DC1
                      |
                 WAL streaming
                      |
                WAN / VPN
                      |
                      v
                   DR DC2
                      |
                 DR Standby
```

The DR replica should be tested—not merely installed.

---

# 20.32 DR Testing

At defined intervals:

```text
Replication validation
Backup validation
Restore validation
Standby promotion
Application connection testing
DNS/VIP validation
RPO measurement
RTO measurement
Rollback/reintegration
```

A DR environment that has never been tested should not be treated as proven.

---

# 20.33 RPO Test

Record:

```text
Last committed transaction on primary
Last replayed transaction on DR
```

Calculate the actual observed recovery point.

Example:

```text
Primary:
10:00:00

DR replay:
09:59:58

Observed exposure:
~2 seconds
```

This is an example methodology, not a guaranteed PostgreSQL value.

---

# 20.34 RTO Test

Measure:

```text
T1 = failure detected
T2 = fencing completed
T3 = standby promoted
T4 = routing changed
T5 = application restored
```

Then:

```text
RTO = T5 - T1
```

This gives you a measured RTO rather than a theoretical one.

---

# 20.35 Connection Routing

Applications should not be hard-coded to a single physical primary where possible.

Architecture:

```text
Application
      |
      v
Connection Pool / Routing
      |
      +----> Primary
      |
      +----> New Primary after failover
```

Possible mechanisms:

```text
DNS
VIP
Load balancer
Connection pooler
Service discovery
Cloud endpoint
```

The correct mechanism depends on infrastructure.

---

# 20.36 DNS Failover

Example:

```text
db-prod.company.com
        |
        v
     PRIMARY
```

After failover:

```text
db-prod.company.com
        |
        v
   NEW PRIMARY
```

Be aware of:

```text
DNS TTL
Client DNS caching
Connection pool behavior
Existing TCP connections
```

Changing DNS does not instantly move already-established database connections.

---

# 20.37 VIP Failover

Architecture:

```text
          VIP
           |
           v
       Active DB
```

After failover:

```text
          VIP
           |
           v
     New Active DB
```

This can simplify application connection strings, but requires reliable fencing and network infrastructure.

---

# 20.38 Backup + HA + DR

Correct architecture:

```text
             PostgreSQL
                  |
        +---------+---------+
        |         |         |
        v         v         v
       HA        DR      BACKUP
        |         |         |
      Fast      Site     Point-in-
      failover  failure  time recovery
```

Do not assume:

```text
HA = Backup
```

or:

```text
DR Replica = Backup
```

A replicated accidental `DELETE` can propagate to the standby.

A backup/WAL recovery strategy provides a route to an earlier recovery point.

# 20.41 Post-Failover Validation

Run:

```sql
SELECT version();

SELECT pg_is_in_recovery();

SELECT current_database();

SELECT now();
```

Then validate:

```text
Can applications connect?
Can writes execute?
Are critical tables accessible?
Is WAL generation functioning?
Are backups functioning?
Are monitoring alerts cleared?
```

# 20.42 Rebuilding Former Primary

Do **not** simply restart the old primary and attach it blindly.

After a promotion, the old primary's timeline differs.

The former primary generally needs to be safely re-established as a standby using an appropriate recovery/rebuild procedure.

A common approach is a fresh base backup from the new primary:

```text
NEW PRIMARY
     |
     | pg_basebackup
     v
OLD PRIMARY
     |
     v
NEW STANDBY
```

This is operationally safer than assuming the old primary can immediately resume replication.
